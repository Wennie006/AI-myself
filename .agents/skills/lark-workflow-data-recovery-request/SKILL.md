# 数据回收需求文档撰写工作流

**CRITICAL — 开始前 MUST 先读取 [`../lark-doc/SKILL.md`](../lark-doc/SKILL.md)，本 skill 只讲"诉求内容怎么写"，fetch/update 的机制细节以该 skill 为准。**

## 适用场景

- "帮我写一份数据回收文档"
- "这个需求上线后，要跟数仓/BI 要哪些数据，帮我整理一下"
- "帮我完善这份数据回收文档"（已有草稿，参考同类文档补全）
- 用户给了一个 PRD 链接，要求产出配套的取数需求文档

## 核心原则（务必遵守，均为真实踩坑总结）

1. **读者是数仓/BI，不是产品或后端**。诉求部分绝不能出现产品需求点式的语言（例如把"扩大补贴范围""优化引导策略"这种功能描述当成条目标题）。哪怕 PRD 原文就是这么写的，翻译给数仓看的必须是"要拉哪类订单、按什么口径过滤、怎么计算"，不是在解释这个功能是做什么用的。
2. **每一条必须独立、自包含，禁止要求数仓自己排列组合**。不要写"上面第 1、2 条数据再按 XX 维度拆一下"这类跨条引用；也不要用多层嵌套编号（a/b/c 套 i/ii）逼读者在脑内把树状结构摊平。数仓一眼扫过去，每一行就该知道自己要拉什么、按什么条件过滤、怎么算，不需要跳到别的条目拼凑。
3. **格式优先用单层有序列表，不用表格，也不用深层嵌套**。表格看起来规整，但字段/备注一多就会列爆炸或单元格塞不下说明；深层嵌套则强迫读者做"排列组合"。最终收敛的最佳实践：**一层有序列表**，同一批订单/统计对象相关的多个指标（如订单数、出票订单数、出票量）合并写在同一条里、用顿号"、"隔开；需要按维度拆分时在句尾用括号注明，不单独起一条。用户明确要表格时才用表格，且同样要遵守"自包含、不用组合"的原则（每个单元格独立可读，不依赖跨行/跨列推理）。

## 文档结构模板

标题：`{需求名称} 数据回收`

```
# 1.需求背景：
{从 PRD 提炼：这次需求做了什么改动/上线了什么策略，1-2 句概述背景数据（如日均目标量、当前转化率）}

# 2.需求目的：
{这份数据回收要验证/回答什么问题，通常是"验证是否达成预期目标（目标 XXX，实际转化 XXX）"}

# 3.诉求：
按天回收以下指标：
1. {指标 1，自包含完整表述}
2. {指标 2、指标 2 的关联子指标 a、子指标 b（需要按维度拆分时括号注明）}
3. ...

原需求文档：{PRD 的 <cite> 引用}
```

**分母类指标放第 1 条**：满足统计条件的基础订单/用户群体规模（作为后续所有指标的分母/统计范围），独立成第一条。

**每条指标的内部结构**：`{订单群体/统计对象} + {动作/条件} 的 {指标名}（+ 附加口径说明）`。同一群体强相关的"数量、出票订单数、出票量"等指标合并到同一条，用"、"连接；不同群体/不同统计对象另起一条。

## 工作流

```
PRD 文档 ──(lark-doc +fetch --scope section)──► 提炼背景/目的/需求点
                                                        │
                                                        ▼
                                          按"核心原则"翻译为数仓取数语言
                                                        │
                                                        ▼
                                    起草诉求列表（自包含单层有序列表）
                                                        │
                                        ┌───────────────┴───────────────┐
                                        ▼                               ▼
                              新建文档：docs +create           已有文档改写：docs +update
                                                              （先 +fetch --detail with-ids
                                                               拿最新 block-id 再改）
                                                        │
                                                        ▼
                                    docs +fetch --scope full 校验渲染结果
```

### Step 1：吃透 PRD

```bash
lark-cli docs +fetch --doc "{PRD_TOKEN}" --scope section --start-block-id {需求背景/需求点章节ID}
```

提炼：改动前 vs 改动后的策略差异、目标数值（如目标订单量、目标转化量）、涉及的产品/业务对象（产品 ID 等，如 PRD 有则一并列出；缺失就在草稿里明确标注"待确认"询问用户，不要瞎编）。

### Step 2：起草诉求列表

对照"核心原则"和"文档结构模板"逐条写。写完自查：

- [ ] 有没有出现产品需求点式的命名/解释性语言？→ 删掉，换成取数动作描述
- [ ] 有没有条目要求读者结合其他条目才能理解？→ 拆开重写到自包含
- [ ] 是否用了表格或多层嵌套？→ 除非用户明确要求，默认改成单层有序列表
- [ ] 强相关指标（数量/出票订单数/出票量等）是否已合并到一条？

先写入本地 `.xml` 草稿文件（复用 [`lark-doc 创建工作流`](../lark-doc/references/lark-doc-create-workflow.md) 或 [`+update`](../lark-doc/references/lark-doc-update.md) 里的写法约定），不要直接拼命令行字符串。

### Step 3：写入飞书文档

- 全新文档：按 [`lark-doc 创建工作流`](../lark-doc/references/lark-doc-create-workflow.md) 执行。
- 已有文档改写诉求部分：**每次写入前必须重新 `+fetch --detail with-ids` 拿最新 block-id**，不要复用对话历史里缓存的 id——文档可能已被用户或他人并发编辑，revision 会跳号，旧 id 可能已失效或指向错误内容。用 `block_replace` 替换整个诉求列表，`--start-block-id` 取第一条 `<li>`（或首个 block），`--end-block-id` 取最后一条（通常是「原需求文档」引用所在 block）。

### Step 4：校验

写入后必须 `docs +fetch --scope full --detail with-ids` 重新拉取，核对：

- 条目数量、顺序、文字是否与草稿一致
- 有没有因为 XML 格式问题导致内容被截断或吞掉（尤其是同一次 `+update`/`+create` 调用里如果混了画板等复杂 block，要格外小心整份文档被静默截断，参见 [`lark-doc-whiteboard.md`](../lark-doc/references/lark-doc-whiteboard.md)）

## 示例（黄金参考）

`B4LUwbfBpifDU8kgpeDcNTu8n5c`（"改单限制支付宝支付 数据回收"）是经过用户多轮修正后最终收敛的范本，格式与措辞可直接参考：

```
诉求：
按天回收以下指标：
1. 满足条件的订单数（原单非支付宝支付）
2. 成功购买1折特惠初阶帮抢的订单数（含支付宝预付+信用付）、出票订单数、出票票量（区分来源为速度模块入口&专人托管服务入口）
3. 成功购买特惠进阶/高阶/全能帮抢的订单数（含支付宝预付+信用付）、出票订单数、出票票量
4. 引导权益升级浮层曝光量、点击量、经由引导弹窗完成购买（转化为支付宝支付）的订单数、出票订单数、出票票量
5. 成功通过支付宝改单补款的订单数、出票订单数、出票票量
原需求文档：[PRD 引用]
```

## 反面案例（曾经踩过的坑，禁止再犯）

| 错误做法 | 问题 | 用户原话 |
|---|---|---|
| 诉求条目用"扩大补贴范围"这种产品需求点做标题分组 | 数仓不需要知道功能叫什么名字，要的是取数逻辑 | "诉求怎么会是'扩大补贴范围'呢？这是给数仓取数的需求啊又不是给后端开发的" |
| 多层嵌套列表（a/b/c 套 i/ii），并让某条写"上面 1.b、1.c 两组数据再按 XX 拆一下" | 逼数仓自己去组合/回溯理解 | "不要让bi自己排列组合，你每一条就写清楚" |
| 把列表改成表格但字段拆得很碎 | 用户体感上一度觉得表格更清晰，但最终又改回了单层列表——**表格不是禁用，只是优先级低于自包含单层列表**，用户明确要表格时再用 | "怎么感觉表格形式会更加清晰，用表格形式呈现试试看？"（用户随后自己又把它简化改回了列表） |
